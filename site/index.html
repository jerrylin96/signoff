01

A reverse interview, not a rubber stamp

Run /signoff from the branch you want to merge. The agent reads the full diff, then asks you a short series of pointed questions across four fixed axes. Vague answers don’t pass: hand-waving pauses the signoff, the agent explains the mechanics, and re-probes with a concrete scenario.

The goal is preventing cognitive surrender — merging AI output nobody actually understands. Intentional trade-offs pass, once you show you understand their boundaries and own their risks.

AXIS 1Mechanics & intent

What changed, and why this design over the alternatives?

AXIS 2Trade-offs & edge cases

What approximations were made — and are they intentional?

AXIS 3Boundaries & failure loudness

Where does it break, and does it break loudly or silently?

AXIS 4Ownership

Do you explicitly accept responsibility for results and risks?

For software engineers

The default profile probes algorithmic complexity, data-structure invariants, and API contract changes — the places engineering diffs fail.

For scientists & researchers

Research code rarely crashes; it produces plausible-but-invalid results. A unit slip between hPa and Pa, an emulator that quietly leaks energy, a trend that vanishes at higher resolution. Any diff touching scientific computation automatically triggers probes on units, numerical stability, statistical validity, and reproducibility. signoff never claims the science is right — it verifies that you know the assumptions and validity regimes. That’s the part a human must own.

02

A record that outlives the branch

When you pass, signoff writes an empty signed commit plus a mirrored git note (refs/notes/signoff) carrying flat, machine-parsable trailers: the reviewed commit and tree SHAs, the acknowledged trade-offs and risks, a SHA-256 digest of the interview transcript, your identity, and exactly which question set you were held to.

Verification survives squash merges and branch deletion via the reviewed tree SHA and the notes mirror. The protocol — the Git Signoff Attestation (GSA) spec — is open, harness-, model-, and vendor-neutral: any tool can produce or verify attestations, and the record lives in your repository, not on anyone’s server.

It does not claim unforgeable proof of cognition, and it does not claim the code is correct. It claims something auditable: a named human demonstrated comprehension and accepted accountability — and here is the tamper-evident trail.

03

Auditing & retrieving interview transcripts

Git signoff attestations bind the interview transcript's SHA-256 digest into immutable git history and notes. Transcripts remain locally on the reviewer's machine for privacy. Anyone — leads, reviewers, compliance officers — can verify or audit the transcript at any time using a simple three-step loop.

Step 1: Auditor requests interview transcript snapshot

The auditor spots the attestation on the commit or PR and asks the employee or reviewer to export the session transcript for verification.

Step 2: Reviewer exports transcript snapshot

On the machine where the signoff interview took place, the reviewer runs the verifier with --audit and --export to extract the exact byte snapshot:

python3 verify/verify_signoff.py --audit HEAD --export transcript.jsonl

The verifier verifies that the local session transcript matches the commit's Signoff-Transcript-Digest and writes the snapshot to the target path.

Step 3: Auditor verifies snapshot against git trailers

The reviewer sends transcript.jsonl to the auditor. The auditor verifies the received transcript against the git trailers:

SIGNOFF_TRANSCRIPT_FILE=transcript.jsonl python3 verify/verify_signoff.py --audit HEAD

Output confirms the transcript digest matches byte-for-byte:

✅ VALID MATCH: Transcript SHA-256 matches sha256:1675b6...
  Harness: claude-code
  Conversation ID: 979cb45-session
  Bytes verified: 8432
  Exported snapshot to: transcript.jsonl
04

Install: one folder, committed to your repo

The skill lives in the repository under review — no plugins, no downloads, nothing account-scoped. Then, from the branch you want to merge, type /signoff (adaptive default auto-selects intensity; --deep for skeptical rigor, --quick for low-risk diffs).

Any repository — zero-touch

The initializer vendors the skill into .claude/skills/signoff/ or .agents/skills/signoff (use --skill-target {auto,claude,agents,both} to control destinations), scaffolds the CI gate and interview profile, and opens a ready-to-merge branch.

curl -fsSL https://raw.githubusercontent.com/jerrylin96/signoff/init-v5/init.py -o /tmp/signoff-init.py && python3 /tmp/signoff-init.py

Any repository — manual

Copy skills/signoff/ to <your-repo>/.claude/skills/signoff/ and commit. That is the whole install for Claude Code — CLI, desktop, and claude.ai web/cloud sessions, for every collaborator.

Other harnesses — Antigravity, Codex, Goose, …

The skill is a self-contained folder of prompts: copy skills/signoff/ into your harness’s skill location and set the transcript adapter env vars. Full matrix in HARNESSES.md.

04

Make the interview yours

The four axes are fixed for everyone. What you customize is the interview profile — a single delimited text block that weights the questions toward your domain’s failure modes. Profiles can add emphases but can never remove axes or lower pass criteria: a customized interview is never a weaker one.

  1. Create .signoff/profile.md in your repo

    The repository being reviewed carries its own question emphasis — for every collaborator, on every harness, surviving skill updates.

  2. Start from a shipped profile

    Paste in domain-science (research code) or software-general (classic engineering) — or rewrite the bullets to name your failure modes: conservation properties of a new parameterization, grid-resolution sensitivity of a reported trend, leakage between reanalysis training and evaluation periods.

  3. Done — provenance is automatic

    Every attestation records which question set actually ran, with a content digest for repo-supplied profiles — so a diluted profile is always distinguishable from a shipped one.

    # in the attestation trailer:
Signoff-Agent: … interview=standard/your-lab-id/sha256:5fd075753d5b
05

Show your work is answered for

A two-minute CI check verifies GSA attestations against your repository’s history: pull requests fail until the branch ends in a valid attestation, and your README carries the badge.

attested by humanspassing Green means: a named human understood this code and accepted accountability — no more, no less. 
# .github/workflows/signoff.yml
name: attested by humans
on:
  pull_request:
  push: { branches: [ main ] }
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: jerrylin96/signoff/verify@main

The verifier is a single dependency-free Python file — copy it into any CI system. Details: verify/.
